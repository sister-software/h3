# sister-h3

An independent Rust implementation of the [H3](https://h3geo.org) hexagonal hierarchical
geospatial index, translated from the H3 C library (pinned at `v4.5.0-67-g24946ad1`) and
verified against it: bit for bit on linux x86-64 glibc, within documented bounds elsewhere.

```toml
[dependencies]
sister-h3 = "1.0"
```

```rust
use sister_h3::{CellIndex, LatLng, raw};

let cell = CellIndex::from_lat_lng(LatLng::from_degrees(37.3615593, -122.0553238), 7)?;
assert_eq!(cell.to_string(), "87283472bffffff");

// C-equivalent functions over raw u64 indexes return C error codes.
assert_eq!(raw::cell_to_parent(cell.get(), 9).unwrap_err().code(), 12);
# Ok::<(), sister_h3::H3Error>(())
```

- `sister_h3::raw` mirrors the C API (snake-case names, `Result<T, H3Error>`), including C's
  behaviour on unvalidated input and C output-buffer shapes for disks, rings and polygon fill.
- `CellIndex`, `DirectedEdgeIndex`, and `VertexIndex` validate on construction and support text parsing and raw-index conversion.
- Cells expose typed disks, rings, paths, distances, and area measurements. Traversal iterators omit unused C buffer slots.
- Resolution arguments remain `i32` for compatibility and are validated by each operation.
- Angles are radians; use `LatLng::from_degrees`, `degs_to_rads`, and `rads_to_degs` to convert.
- No `unsafe`, no C, no JavaScript, and no runtime dependencies by default.

## The `libm` feature

```toml
sister-h3 = { version = "1.0", features = ["libm"] }
```

By default, `sin`, `cos`, `tan`, `acos`, `atan`, and `atan2` come from the platform's libm, the
same library a locally built H3 C uses, so results match C on the same machine (bit for bit on
linux x86-64 glibc). Math libraries differ in the last bits, though. A point within about 1e-14
radians of a cell edge can land in a different cell on macOS, Windows, Android, or musl than on
glibc.

With the `libm` feature, those six functions come from the pure-Rust
[`libm`](https://crates.io/crates/libm) crate. Results are then identical on every platform and
identical to the `@sister.software/h3` WebAssembly build, which enables the feature. Use it when
derived data must reproduce exactly across machines. It is typically somewhat slower than the
platform libm (see `benchmarks/RESULTS.md`). Cargo features are additive, so one crate enabling it
turns it on for the whole build. Polygon order from `cells_to_linked_multi_polygon` is unspecified
and can differ between the two.

The crate's tests compare every operation with fixtures generated by the pinned C library
(`tests/fixtures`). The JavaScript and WebAssembly package lives in the same repository:
`@sister.software/h3`.
